## [Unreleased]

### Added
- **A constraint the model has to remember is a suggestion; the constraint now lives below it** (`1e2f1fe`, 21 files, +6,324): an agent told "never query the live database" obeys for as long as the sentence survives in its context, and nothing in the loop notices when it stops. The requirement was a rule that cannot be side-stepped, one that can be filed *mid-run* by whichever worker is about to repeat the mistake, one whose refusal says where to go instead, and one whose knobs a person can tune without opening a source file. All four shipped. Rules live in `velocity-mcp/src/rules/` as five kinds (`tool_ban`, `egress_ban`, `path_ban`, `command_pattern`, `tool_budget`) across three scopes (task — process memory; workspace — `<workspace>/.velocity/rules.json`; global — the user config file), and enforcement is not a prompt: `rules::gate_tool_call` runs from `registry::call_tool_in_workspace`, the one path every MCP client and the embedded agent share, before the handler is reached, so the model cannot talk its way past a wall it can still describe. Scopes are evaluated task → workspace → global and the first blocking rule wins, which is what lets a run shadow a broader rule instead of being smothered by it. Rule files are re-stamped (mtime and size) on every call and reloaded when they move, so a rule written by one process binds the next call of every other without a restart — the reason the whole subsystem is useful rather than merely tidy. Two properties keep a rule honest: it cannot be inert and it cannot be a dead end. Creation runs a witness pair — one call the rule must block and one near-miss it must allow — evaluated against the rule in isolation before the version is written, so an egress ban on a host no argument form reaches, or a command pattern written as a regex, is refused at creation instead of quietly doing nothing for a month; and a rule file that exists but does not parse fails **closed**, refusing every call with the path and the parse error, because a silently disabled safety rule is worse than a stopped pipeline. The refusal is directional by construction: `description` (required) and `remedy` are stored and quoted verbatim, and the live sentence the gate emitted on the rebuilt binary was, word for word — `action blocked — server "192.168.1.100"; rule "live-db-off-limits" (workspace, rule-8fbea320): The host at 192.168.1.100 is the live production database; nothing in this workspace may send traffic to it. Query the dev database instead. Remedy: use the dev database at 192.168.0.2.` — while the same probe's call to the remedy address passed the gate untouched and failed later, in PowerShell, for having no `psql` installed. Authority is one-directional too: versions are immutable (an adjust writes v2 and keeps v1, a retire is a tombstone, so "which rule was in force on Tuesday" stays answerable), an agent may create or tighten immediately but may only *propose* a loosening, and Approve/Reject exist solely behind Settings → Rules — no tool argument reaches approval, and a bypass is a separate expiring grant (event = exactly one call, session/workspace = up to 10,080 minutes) rather than a flag on the rule. The panel (Active / Pending / History, refreshing itself whenever the files' revision moves, so an agent's mid-run rule appears without a restart) carries kind-appropriate widgets — comma-separated lists for the bans, **Tool calls** 1–100,000 and **Window** 1–10,080 `min` for a budget — and shows the refusal the rule will produce before it is saved. Ninety unit cases cover it: `matcher` 13 (an IPv4 inside a shell command, a URL host, a CIDR range, a scheme-less `-h host`, the dev server allowed, path-component boundaries, case-insensitive command text, an empty target list that must never match), `engine` 9, `lifecycle` 15 (agent adjust pending and applying nothing, user adjust keeping the old version, approving once, retiring as a tombstone, grant expiry and the cap), `store` 10 (atomic round-trip, corrupt file failing closed, a BOM tolerated, the revision moving, task rules per-workspace in memory, an event grant consumed exactly once), `verify` 8 (each witness rejection), `model` 8, the gate's own verdicts in `rules/mod` 5 (the directional refusal, the dev server allowed, a single-use grant, a corrupt file refusing every call, and a global rule binding where no workspace file exists), `rules_tools` 11 and the panel's own 11, two of which are the panel meeting the engine through the same entry point `call_tool_in_workspace` calls: a rule created from the form blocks the next call and its near-miss passes, and saving a tightened budget rebinds the gate on the next call. The full `velocity_mcp` lib suite ran 3,698 passed / 0 failed / 22 ignored at the commit, and `cargo clippy -p velocity_mcp --all-targets -- -D warnings` is re-verified clean on `main` today (exit 0, 2m23s; the only line in that log is the pre-existing `proc-macro-error2` future-incompat notice, not a lint). Two defects fell out of building it. The first was found by the live pass: the budget refusal sentence was being assembled in more than one place, so what an agent read when it filed a ceiling was not what the gate later sent — the panel and `rule_create` now both render through `engine::budget_detail`, the same function the ceiling calls, which is why the probe above reads `tool-call budget exceeded: 3 calls in 60 min (limit 2)` at creation and at fire time alike. The second was a side effect of placement: the eight `rule*` tools ship on the always-on core floor, because the worker that can record the rule is the one holding the banhammer, and that floor was exactly twelve tools — nine files plus three shell — which is precisely `PROSE_SURFACE_LIMIT`, the count that decided whether the inline tool catalog kept its per-parameter prose. Eight more tools on the floor made every narrow surface, even a bare one with no group requested at all, fail a test it used to satisfy by landing on the boundary, silently stripping the guidance (`edit_file`'s verbatim-match parameter is exactly the kind that needs it) from every run that was not broad. The test is now on what is actually being bounded, characters of the rendered catalog (`PROSE_CHAR_BUDGET = 14,000`; measured over the registry, 347 tools and 1,183 parameter descriptions render 141k characters ≈ 40k tokens against 85,739 compact), so adding a group can no longer cost a run its instructions by arithmetic. What this does not cover is stated in `docs/rules-engine.md` and is worth repeating here rather than discovering later: nothing compiles to an OS firewall, so an `egress_ban` polices calls that reach the gate and not a process the agent spawned that opens its own socket; a `tool_budget` window is per process and per rule version, so two IDEs open on one workspace keep two counters (the probe's own counts ran 3, 4, 5 inside a single process) and re-tightening a budget starts its window afresh; task rules die with the process; lifecycle triggers (post-build, pre-commit) are not expressible yet, though the schema is additive; and the legacy `.velocity/policy.json` engine keeps running at the same choke point — the two are additive, and migrating one into the other is separate work.
- **A green grade now has to account for the source, not only for the Rust**: every gate the loop runs judges Rust — the build, the test tally, the module graph — and none of them can see where the bytes came from, so a conversion whose named source never reached the model was certifiable. Live run #101 is what that costs: the dispatch named `litellm/router_utils/pattern_match_deployments.py`, the preload could not read it, the brief carried `[Could not read …]` in place of its bytes, and the model then spent five consecutive turns (`Turn 6`–`Turn 10`) asking for `read_file` and answering itself `Exploration locked — refused 'read_file'`. It wrote 327 lines of Rust in which none of that module's names appears — `PatternUtils`, `pattern_to_regex`, `calculate_pattern_specificity`: zero occurrences each — and the dispatch returned `success: true` quoting `Repair validated — test result: ok. 186 passed`. The loop now reads that fact back out of the brief it assembled itself: the preload section's `### path` heading whose body is the unreadable marker, parsed section-scoped and fence-aware so a source file that quotes the marker is not blamed for its own contents; it remembers every `read_file` that returned bytes; and a deliverable whose named source is in neither list is refused at both exits — the per-turn write gate and the post-run validation. The reply names the path and offers the only two moves that are true on that evidence: find and read the source (`list_dir` along what the run can see, `glob_search` for the file name) and rewrite the deliverable against its real class and function names, or end the run saying the source is unavailable. Two steering turns, then the run stops `Blocked` with the path on record instead of a tally borrowed from the crate's other modules. Three details keep that refusal honest rather than merely strict: a read counts by file name and not by the exact path the brief quoted, because the same module is usually reachable under a second root; a source the run wrote itself is not one it owed a read of; and the whole guard arms only where the run has an artifact contract, so a chat turn that named no file is untouched. The refusal deliberately does not arm the compile-repair lock — either field that would bring it also brings the next turn's exploration lock, and the one move this directive asks for is the `read_file` that lock forbids; #101 measured that lock from the wrong side and then wrote the port from memory. Eleven unit cases cover the provenance half — the parser's fence awareness, its section boundary, the marker read back from the producer that writes it, the basename match, the self-written exemption, the budget and the failure label; seventeen non-vacuity splice rounds each delete one clause and each turn their own test red with the source restored byte-exact. Two end-to-end cases drive the production dispatch path: `unread_source_refuses` (14/14 — the marker present in request 0, the steering needle in the later request bodies, `(1/2)` and `(2/2)` and `Deliverable is NOT validated` in the stream, `Repair validated` nowhere in it, `cargo check` and `cargo test` green on bytes nobody read) and `unread_source_read_clears` (13/13 — the same withheld grade, then a `read_file` of that file name at a path the brief never named, and the grade lands as `Repair validated — 150 passed`, which is also the proof the refused turn was never locked). Deleting the wiring and rebuilding costs each case its own half of the proof, with a case that does not depend on the clause as the control: gut the withheld grade and the refusal case comes back 4/14 with the run ending green after one turn — run #101's false green, reproduced — while the unrelated off-target case stays 5/5; stop recording reads, or re-arm the refusal as a repair directive, and the clearing case comes back 9/13 (no `Repair validated`, `(2/2)` and `Deliverable is NOT validated` in its place, the model's `read_file` refused) while the refusal case stays 14/14. Restoring the source and rebuilding returns both to 14/14 and 13/13. That pair found one defect of its own: a gate verdict carrying no rustc diagnostics — both the never-read-source and the never-declared report — wrote the handover note as `The source was never read: ` with nothing after the colon, because the note joined an empty signature list. Such a note now quotes the report's own first clause, framing stripped and one clause bounded to 240 characters, while a report that does have diagnostics keeps being quoted by them; three more unit cases, one per behaviour. What this does not prove is the other half of the claim: that a port which looked at its source is *faithful* to it. Run #101b, the same binary with the preload correct, measured exactly that — the model was handed the real module, 8,954 bytes as the preload read it (9,203 on disk; the difference is its 249 CRLF pairs collapsing to LF) and produced Rust naming `pattern_to_regex` 76 times, `add_pattern` 57 and `PatternUtils` 49 across a 158,727-character transcript, entirely as chat prose with zero tool calls. The 900 s uncommitted-turn clock cut two streams (~19,943 and ~17,080 tokens), the run's two-cut allowance was spent, and the dispatch ended `success: false` with `blocked_reason: reply cut for streaming without a tool call`, the deliverable at 0 bytes and the crate re-measured at its baseline 170 passed. Nothing was falsely certified — that is what the gates above are for — and about 1,800 s of a faithful port was discarded on the way to that honest verdict. Re-baselined against this same binary, live run #104 converted `litellm_core_utils/get_provider_specific_headers.py` — 1,667 bytes of Python, read by the preload and already declared in `lib.rs` — in one turn: `Turn 1: model 425.5s + tools 2.2s (1 call(s))`, 446.7 s of dispatch, `ramble_turns: 0`, `degraded: false`, and a 10,199-byte, 279-line artifact carrying 9 `#[test]`s and zero `unimplemented!` or `todo!`, with the grade landing as `Repair validated — test result: ok. 179 passed` against the crate's recorded 170-passed baseline (re-measured by hand, same figure). Neither new gate fired, which is the non-interference half of the proof: both withhold a green, and a false withhold costs a run exactly like a false one does. Read beside #101b, the pair says the remaining gap is not model competence — 8,954 bytes of source became chat prose and a 0-byte deliverable, 1,667 bytes became a compiling port in a single write turn — it is the size of the port measured against what one turn can commit, so #103 is a batching problem before it is a salvage problem. Two figures in that rollup are also worth naming so nobody reads them as findings: `wall_clock_limited: true` is only `budget.is_some()` echoed back (`team_tools.rs:3570`; I passed a 2400 s budget) and the one warning in the build comes from the pre-existing `litellm_core_utils_dot_notation_indexing.rs:157`, not from this module. What #104 still does not prove is the same thing #101b could not: faithfulness is mine to check and not the loop's — I read those 279 lines against the Python and they agree on the `None` short-circuits, the comma split with `strip()` and the later-wins `update`, but no gate in the loop can see that, and one small module is n=1 against a repo of hundreds. The next gap is the discarding: a turn whose port arrives as prose should have its fenced block salvaged into `write_file`, or be steered to it, rather than end the run.
- **The module-graph grade now reads a cargo workspace, which is the shape a large conversion grows into**: the gate above walked the graph from the manifest's own directory, and a `[workspace]` root names no lib target there — so `crate_roots` came back empty, the walk abstained, and a port left undeclared inside `crates/router` was certified by the member's clean build. The same false green, one directory level deeper, in exactly the layout a LiteLLM-scale rewrite ends up in. The loop now resolves every crate directory one manifest builds (its own, plus each `[workspace]` member with `*` globs expanded against the filesystem and `exclude` honoured), owns each written file by the **deepest** crate that holds it, and unions every crate's roots into one compiled set. Two details make the verdict usable rather than merely correct: the root it names is the path the agent has to type — `crates/router/src/lib.rs`, because `edit_file` resolves workspace-relative and a bare `src/lib.rs` at that root does not exist — and orphans in two member crates come back as one refusal naming both, so no run is told to declare a module in a crate that cannot see its file, which would end in E0583 instead of a build. A virtual workspace root (no lib target of its own) is deliberately not an owner: claiming it would put every file in the tree "inside a crate" and refuse the ones outside every member with a verdict no root file can answer. Nine unit cases cover the glob, the exclusion, the deepest owner, walking every member rather than the first, a multi-line `members` array, the two-crate verdict, cargo's own `path =`/`tests/` exemptions and the no-member abstention; nine non-vacuity splice rounds each turn their own test red with the clause deleted and the file restored byte-exact. The end-to-end case (`undeclared_workspace_member`) runs the previous entry's script inside a real `crates/*` fixture workspace, 11/11: the run is refused while it is still working — "The build is clean, but the crate that builds never compiled crates/router/src/orphan_ws_case.rs — no mod declaration in crates/router/src/lib.rs reaches it (1/2)" — the fix reaches the request body as "Add pub mod orphan_ws_case; to crates/router/src/lib.rs", and the crate's measured tally goes 1 passed → 3 passed only once that line lands. Deleting the member resolution and rebuilding takes the case back to the abstention — 6 of its 11 assertions lost, while the single-crate case, which needs no member resolution at all, stays 11/11; that control is what makes the loss the workspace's own. Deleting only the relative label costs the same two needles in both cases (9/11 each, because one helper writes the label for every crate): the refusal still arrives, it just points at a `src/lib.rs` nobody can type from that root, whether the orphan sits in `crates/router` or in the one-crate workspace. That relabelling also corrected the earlier case's needles in passing: its verdict used to tell the model to edit `src/lib.rs` in a workspace whose root has no such file.
- **A clean build no longer certifies a file the crate never opened**: `cargo check` grades a module graph, and a `.rs` the agent wrote that no `mod` declaration reaches is simply not in it. Live run #26 is what that costs — after three models had been cut for rambling, the fourth wrote a 24-line scaffold to `rust_port/src/router_utils_pattern_match_deployments_py.rs`; the crate, whose `lib.rs` declares that module *without* the `_py`, built clean and passed the 170 tests its seed modules always passed, and the dispatch reported `success=true` quoting that tally. The off-target rule could not see it: the write landed exactly where the brief said it should. The loop now walks the graph from the crate root — every `mod`/`pub mod` hop, each `#[path = "..."]` redirect, the files a manifest names with `path = `, and the targets cargo builds unaided (`tests/`, `benches/`, `examples/`, `src/bin/`, `build.rs`) — before it accepts a green grade at either exit, the per-turn write gate and the post-run validation. A grade resting on somebody else's modules is withheld and answered with the one line that fixes it, `pub mod <name>;` quoted against `src/lib.rs`; after two steering turns the run stops with the refusal on record rather than a borrowed tally. The gate abstains when there is no manifest or no root to walk, and never claims a file outside the crate it runs in — a false refusal spends a repair turn from a run that earned its green. (A multi-crate `[workspace]` root was in that abstaining class when this shipped; the entry above closes it.) Eight unit cases, seven non-vacuity splice rounds (refusal, `#[path]`, the nested-`mod` candidate, the no-root abstention, cargo's `tests/` target, the outside-crate abstention, the failure label — each removed singly, each turning its test red) and two end-to-end stub cases, one per exit, that fail from green to refusal when the predicate is deleted and the binary rebuilt. The graded tally moving 170 → 172 the moment the declaration lands is the measurement the gate exists to make.
- **Playbook and workflow reference validation** — a three-layer defense sharing one code path (`validate_step_references`): write-time rejection in `add_org_playbook`, pre-flight failure in `run_playbook` / `workflow_run` / the GUI Run button, and a batch `validate_org_playbooks` MCP tool plus a dashboard summary line. Every `Tool` step is checked against the live registry and every `Connector` step against `.velocity/connectors.json`, recursing into ForEach bodies; a broken SOP can no longer half-execute side effects before hitting a ghost name.
- **`workflow_list` MCP tool**: saved workflows with per-step-type counts and validation issues flagged, closing the discovery gap that left `workflow_run` callable only by guessing ids.
- **Step-type breakdowns everywhere workflows render**: the org dashboard, `list_org_playbooks`, the `workflow_list` output, the workflow editor panel and the template gallery now show `(T# C# A# F#)` counts instead of bare step totals.

### Changed
- **The tool census agrees with itself, and Settings → Rules is documented for a person who has never read the spec**: shipping the rules engine left three documents each holding a different number. `docs/manual/mcp-tools.md` carried nine per-category sections whose rows — 355 of them — match each module's inventory in `velocity-mcp/src/registry/tool_definitions/` exactly, while its own summary table still said `team: 27` (the section lists 31) and its header said 351; `USER_GUIDE.md` advertised "336 tools across 7 categories" with a stale System 53 and Team 22; and `docs/rules-engine.md` enumerated seven tools for a surface that registers eight, omitting `rule_kinds` — the one an agent is told to call first. Both counts are now derived rather than remembered: the nine modules sum to 355 and `get_tools()` concatenates exactly those nine plus dynamically registered custom tools, so the reference reads 355 across 9 categories with `team: 31`, and the guide points at that file instead of restating it. The end-user half of the subsystem was the bigger gap — the engine spec is a page and a half of guarantees and the panel had nothing. `USER_GUIDE.md` gains **Runtime Rules** (what a rule refuses, per-kind parameters and their enforced bounds, the refusal quoted as the agent reads it, and the seven things worth knowing before relying on it: it lands on the next call in every agent, an inert rule is rejected at creation, an agent can tighten but only a person can loosen, a bypass expires, a retire has no undo, a corrupt file stops calls rather than rules, and budgets are per process), `docs/manual/settings-providers.md` gains the panel's own **Rules** section and the corrected "five sections" preamble (Appearance · System · Agent defaults · Providers & credentials · Rules, matching the order `render.rs` draws them in), and the manual index and the legacy **Governance** entry now say which of the two engines is which — policy.json stays advisory-and-additive, the rule engine is the one that refuses below the model, and both are enforced at the same dispatch choke point.
- **The MCP tool reference matches the running binary again**: `docs/manual/mcp-tools.md` was missing an entire category — all 44 company-org tools and the new `workflow_list` (291 documented vs 336 live). The `company` section is now generated verbatim from `tools/list`, totals and category tables corrected, and the USER_GUIDE tool counts refreshed (including the long-stale Team figure).
- **Dead-code annotations reduced**: four file-level `#![allow(dead_code)]` (model_quality, instruction registry, wa platform, worker types) retired after verifying the code is fully live, one orphaned runtime function and three redundant `#[allow(unused_imports)]` removed; `dispatch_intervention` is `#[must_use]` so delivery outcomes can't be silently dropped.
- **A turn that never names a tool call is bounded by patience as well as by length**: the guard cut only at ~24000 tokens, and a token costs whatever the route charges for it — measured at 1411 s, 1309 s and 1223 s for three such turns in one 5023 s port dispatch, 79% of the run spent describing work instead of doing it, with no wall clock left by design to end it. The loop now also stops reading at 900 s (`VELOCITY_UNCOMMITTED_TURN_MAX_SECS`; `off` removes it), the status line names the unit that fired, and a reply that has already begun its tool call — delivered as provider call chunks or written as markup inside its own prose — is exempt from the clock, so the new bound cannot become a second way to lose a deliverable mid-write. Re-running the same port with the fix, all six cuts were clock cuts — 901 s to 928 s each — and the token counts they report show why length was the wrong yardstick: ~16,600, ~14,900, ~17,500 and ~16,700 tokens on the llama.cpp route and ~7,100 and ~8,600 on the slower Ollama copy of the same model, all at the same 900 s of patience.
- **The prose allowance belongs to the run, so a fallback chain cannot re-pay it per model**: two cut turns was a per-attempt ceiling, and an "attempt" meant one call into the loop — which is exactly what each candidate in `team_dispatch`'s chain gets. Live run #26 is what that costs: the chain met one set of weights three ways (`qwen3.6-35b-a3b` over llama.cpp, its `.gguf` path, then `qwen3.6:35b-a3b` under Ollama), paid two 900 s cuts for each of them, and spent 5,500 s of a 6,025 s dispatch — 91% — on turns that executed nothing, while the attempt that finally wrote the deliverable was the chain's eighth hop. So the fix bounds the run without ever refusing a candidate on another model's behalf. `RambleLedger { cuts, secs }` now rides the subagent request and comes back on the result: a hop starts where the run left off and stops at the cut that finishes the allowance rather than paying for two more of them, while the ceiling binds only on a turn that was actually cut, so a spent ledger cannot silently shorten the separate announcement budget. A later hop at a model this run has already paid to have ramble is skipped under its normalised name (path, extension and tag separator removed) and the skip is written to the attempt log with its reason — an unnameable candidate is never a duplicate of anything. And every rewound turn now prints the cost line it used to swallow: the six 900 s turns of #26 rolled the index back and printed prose instead of a figure, so summing every `model Xs` in the transcript gave ~620 s against 6,025 s of wall clock. The dispatch reports what it spent on both levels — `ramble_turns`/`ramble_secs` per attempt (the hop's own share, not a running total) and at the top level (the run's) — because a caller who reads only the JSON had no way to see the time at all. Proved by six unit cases and seven non-vacuity splice rounds (the ledger bounds the run and nothing else, the cut count is the bound, a hop is charged its own spend, the cost line carries its seconds, the skip predicate, the name normalizer, the log entry — each removed singly, each turning its test red), plus an end-to-end stub case that drives three candidates at a 3 s ceiling and reads `1 of 2`, `2 of 2`, `3 of 2` in one status stream with the third hop writing the deliverable: 15/15 assertions, `cargo check` and `cargo test` green on the artifact. Deleting the one line no unit test can reach — the loop reading the ledger it was handed — costs that case three of its fifteen assertions, including the `3 rambling turn(s)` needle, and it comes back green on the restored source. What this does not measure: the orchestrator worker's per-pass ledger (same field, restarts by design re-pay the allowance) runs the pipeline branch rather than the routed chain the case drives, and no stub chain ever repeats a candidate name, so the skip arm is unit-tested but not yet seen end-to-end.

### Fixed
- **Machine-local quota state left the index, and the ignore rules that failed to protect it were fixed** (`e049545`): seven tracked files were runtime state — three copies of the same per-machine quota counters (`.account_usage.json` and its NDA twin at the repository root, under `velocity-mcp/memory/`, and under `--editor/memory/`) plus the legacy `.account_state.json` the tracker migrates away from. Every one of them rewrites itself on the next dispatch, so a tracked copy means a permanently dirty tree and merge conflicts in files nobody reads. The four JSON payloads held `"accounts": {}`: nothing of value was in them, which is exactly why nothing was watching.
  Two defects made them committable, and neither was the `git add -A` that did it. The ignore rules were `memory/.account_usage.json` style, and a gitignore pattern containing a slash is anchored to the directory holding the file — so the rules covered one location while `UsageTracker` writes into `<workspace_root>/memory/` for whatever root the process was handed; `velocity-mcp/memory/` was never protected. `--editor/` was a command-line flag read as a workspace path back when the editor lived in `velocity_mcp` and accepted `--editor`; the flag is gone — the binary rejects unknown arguments and has no editor mode, and the editor is `velocity_ide_gui` — but `.wiki/architecture/system_overview.md` still advertised `velocity_mcp --editor`, `velocity_mcp` with no args as the editor, and a `--benchmark` mode, so the document kept recommending the invocation that makes the artifact.
  `UsageTracker::STATE_FILE_NAMES` is now the single list the three paths are built from, and three guards read it from the other side: each name must be ignored at *every* depth (a matcher that models git's anchoring rule, which the old ignore file fails), no name may appear in `git ls-files`, and no tracked path may lie under a `memory/` directory or contain a dash-leading component. The two index guards ask git a question and print that there was no checkout to ask when they cannot.
  Non-vacuity was checked by running all three red first: the ignore guard named `.account_usage.json` as root-anchored-only, and both index guards returned the full seven-path list. `git check-ignore -v` then attributed all four surviving paths to the new lines, the crate suite ran 3759 passed / 0 failed, and clippy was clean under `-D warnings`.
  *What this does not prove:* that nothing else can regenerate a dash-leading directory — the index guard and the new `/-*` rule catch and block it, but the argument parser is the real boundary and was not touched here. Nor that `.wiki` is accurate outside the entry-point table, which is the only part read against `main.rs` and the workspace's `[[bin]]` declarations. The untracked files stay on disk: this commit changes what git records, not what the running tracker reads.
- **One provider catalog, and the documents and tests that were counting wrong are now bound to it** (`8df7591`, `09166b8`): `AiProvider` carried seventeen backends while eight places kept their own lists of them — the enum's own label/slug/alias/variant-name lookups, the `list_providers` payload (sixteen), the chat model pill and the Settings dropdown (sixteen each, in two different orders), the workspace credential table (fifteen, plus two declared key-free), the capability table (sixteen rows), the enablement scan (eleven), and the tests that should have noticed, which carried their own copies (`assert_eq!(caps.len(), 16)`, `assert_eq!(table.len(), 15, "16 providers, Bedrock untracked")`, `output.contains("16")`). Every list was correct the day it was written; that is why none of them stayed correct.   The shared-memory face had a third problem of its own: it hand-duplicated the method switch, so it answered a *different* set of methods than stdio. Whether a *tool* failed is not the buffer's business; that is in the payload.

### Fixed
- **The dependency policy had never actually been read**: `cargo deny` only got as far as its own compiler wrapper until this push, so `deny.toml` had never evaluated anything. Given a working rustc it reported findings, all of them real: eight sibling-crate path dependencies carry no version requirement at all, which reads as a wildcard (`*`) under `[bans] wildcards = "deny"`; `Apache-2.0 WITH LLVM-exception` (cranelift, via wasmer) and `0BSD` (enum-iterator, via wasmer-compiler) were absent from `[licenses] allow` — which is not the same as those licenses being unapproved, since an SPDX compound id does not match the bare `Apache-2.0` entry; and `RUSTSEC-2026-0173` marks `proc-macro-error2` unmaintained, reached only through `wasmer-derive`, a proc macro that is not linked into any shipped binary. The wildcards are now versioned, the two licenses are allowed with the reasoning beside them, and the advisory joins the documented ignores next to its eight peers rather than being dropped quietly. `cargo deny check` exits 0 here; the Linux graph carries wayland-side crates this run cannot see, so CI is the first full-forest evaluation.
- **The quarantine job read its own documentation as data**: `.config/flaky-quarantine.toml` has no active entries but shows a commented-out `filter = "safety_concurrent_poison_and_recover"` as a format example, and the step greps for `filter = ` without skipping comments. It therefore asked nextest to run a test that does not exist; nextest exited 4 with `error: no tests to run`, and the job that its own comment calls "a no-op" reported failure. Comments are now excluded, the trailing `|` left by the join is stripped, and `--no-tests pass` keeps a stale entry stale rather than red.
- **Every E2E test failed under coverage, over a path**: `workspace_binary` resolved sibling binaries as `<workspace>/target/debug/<name>`, which is only where cargo puts them when nothing relocated the target dir. `cargo llvm-cov` builds into `target/llvm-cov-target`, so all nine `mcp_stdio` tests died with `failed to spawn velocity_mcp ... No such file or directory (os error 2)` and the coverage threshold was never computed. It now derives the profile directory from `current_exe()` — out of `deps/`, one level up — which holds for a relocated target dir and for `--release` alike, with the old path kept as the fallback.
- **RUSTSEC-2026-0285 (rustls, CVSS 5.3 medium)**: `rustls` was locked at 0.23.42, which accepts TLS 1.3 handshake messages across encryption-level boundaries; the fix is 0.23.45 and this project depends on rustls directly for the browser's TLS stack, so `cargo audit` had been failing on it. Bumped `rustls` to 0.23.45 (pulls `rustls-webpki` 0.103.15). Not ignored, because unlike the entries in `.cargo/audit.toml` this one had a fix available. The `memmap2` 0.6.2 unsoundness audit still warns about is reached only through `wasmer` 5.0.6 (`cargo tree -i memmap2@0.6.2`); the shared-memory IPC uses memmap2 0.9.
- **Three CI jobs were failing because of the compiler, not their subject**: `env.RUSTC_WRAPPER: sccache` was set at workflow level, so every job ran rustc through a binary only three of them install. `cargo deny` reported that as `failed to fetch crates`, the quarantine job as a `cargo metadata` failure, and the Windows GUI sweep as a build failure — all of it `could not execute process sccache ... rustc -vV`, so the sweep had never actually swept in CI. The wrapper is now opted into per job, next to each job's `Install sccache` step.
- **The coverage job never started**: it referenced `zgosalvez/github-actions-report-code-coverage-change@v2`, which no longer resolves (`repository not found`), and GitHub fails a job at *Set up job* for that — so the 45% threshold, the lcov artifact and Codecov had not run in any push, and the coverage gate has never actually been applied. The dead action is gone and the summary `cargo llvm-cov` already prints is written to the run page instead, behind `set -o pipefail` so a threshold miss cannot be hidden by the pipe's exit status.
- **An absolute path was rewritten rather than refused**: `resolve_workspace_path` trimmed a leading `/` or `\` off every path argument, so on Linux `write_file("/tmp/x")` reported success after creating `<workspace>/tmp/x` — a call that did something other than what it was asked, with the containment check never firing. The same input on Windows only failed because `Path::join` substitutes the root for an absolute path and the canonicalize check caught it downstream, so the contract the schemas advertise ("Absolute paths and anything resolving outside the workspace are refused") was enforced by accident on one platform and not at all on the other. Absolute and drive-relative (`C:foo`) inputs are now refused up front, by name, everywhere.
- **Two more lint sites that only a non-Windows target can see**, surfaced once the first pass got that far: the non-Windows `create_or_open` said `.create(true)` without saying `truncate`, and `wa/advanced_input` had an `unneeded return` in the arm that is that function's tail expression there. Neither changed behaviour — `truncate` is off unless requested — so the fix states the intent the Windows arm has always stated (preserve a peer's live buffer across a reconnect) instead of leaving it to be inferred.
- **A refusal test that asserted one particular wording**: `refuses_without_consent` required the literal `requires Windows`, which `wa_virtual_desktop_switch` does not say ("... require Windows 10/11"). It now requires the refusal to name the platform gate instead of a sentence, while the Windows branch keeps its strict demand that the opt-in switch be spelled out.
- **The telemetry IPC only worked on Windows**: off Windows `wait_for_request`/`wait_for_response` were a single 100 µs sleep and `signal_*` were no-ops, so the client read the reply slot before the server had written one and reported `HMAC verification failed` — an authentication error standing in for a missing handshake. The state word is now polled within a bounded budget, which is what the named-event build on Windows already achieves.
- **Five tests asserted Windows path syntax as though it were universal**: `..\..\x` is one ordinary file name on Unix, where `\` does not separate, so a traversal-rejection test passed there by never attempting a traversal; `Path::starts_with` compares components, so a `C:\projects` allowlist prefix matched nothing; and the sitemap recorder escapes `\` but leaves `/` alone, so its expected records were platform-bound. Each now derives the separator from the target it runs on. Two more asserted that a refusal names the opt-in switch, which is the right contract only where consent is the operative gate — off Windows those tools are refused as unsupported before consent is ever asked.
- **Four modules did not lint for a non-Windows target**: `velocity-drone`, `wa/clipboard`, `wa/process_mgmt` and `editor/deploy_pipeline` carried unused imports and parameters inside `cfg(not(windows))` arms that a Windows `cargo clippy` never compiles, so `--target x86_64-unknown-linux-gnu` failed while the local check said clean.
- **`Build`/`Run` could compile a project you never opened**: the palette ran cargo with `current_dir` at the workspace root, and cargo finds a manifest by walking *up*. Opening a folder that has no `Cargo.toml` of its own inside a Rust project therefore meant one palette press compiled — and for `Run`, tried to launch — that entire unrelated project on every core for minutes, during which the control bridge timed out and the IDE read as hung. `Build` also ran a second `cargo check` whose result was thrown away.
