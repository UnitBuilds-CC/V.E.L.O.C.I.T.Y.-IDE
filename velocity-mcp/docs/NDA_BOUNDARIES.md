# NDA and JSON boundary map

This document classifies active V.E.L.O.C.I.T.Y. surfaces as one of:
- **NDA-native**: NDA should be the canonical internal representation.
- **Dual-path**: NDA should exist internally, with JSON preserved as a compatibility adapter.
- **JSON-required**: JSON should remain at the boundary because an external protocol or provider requires it.

The goal is not to replace JSON everywhere. The goal is to make NDA the source of truth wherever doing so improves semantic clarity, determinism, model comprehension, and retained knowledge without breaking interoperability.

## Decision rule

Use NDA when the surface is primarily:
- semantic
- model-facing
- internally persisted
- graph/triple-oriented
- long-lived memory or planning state

Keep JSON when the surface is primarily:
- an external protocol contract
- provider-specific request/response transport
- a serde-driven ecosystem compatibility point
- a shared-memory or RPC frame already consumed elsewhere in JSON form

Use dual-path when:
- we control the internal representation
- external consumers still require JSON
- the same logical object should be available to both the NDA harness and JSON-based tools

## Where NDA improves the system most

### 1. Routed instructions and plans

`task_router.rs` still builds long prose instruction payloads. This is one of the best candidates for NDA because:
- it is generated by the system
- it is consumed by models
- it needs deterministic structure
- it contains repeated semantic fields: goal, scope, route, policy, expectations, root identity

NDA should replace freeform concatenated prose as the canonical task contract, with prose generated only for UI display when needed.

### 2. Reusable instruction and policy memory

The registry is a semantic knowledge base of:
- task kinds
- templates
- decomposition policies
- preferred policy overrides

That is a natural NDA knowledge surface. JSON is acceptable as an export, but it should not remain the authority.

### 3. Semantic browser knowledge capture

The browser crawler already extracts structured information and stores triples. This should stay NDA-first. If anything, it should deepen NDA usage rather than flattening into JSON summaries.

### 4. Internal coordinator memory

Worker outcomes, follow-up states, blocked reasons, accepted scopes, and reconciliation artifacts are easier for agents to reason over if represented as stable structured NDA facts rather than ad hoc strings.

## Where switching fully to NDA would break compatibility

### External provider APIs

Do **not** replace JSON on:
- OpenRouter requests
- Workers AI requests
- streaming provider response parsing
- any OpenAI-style tool call payload expected by third-party APIs

Reason: these are external wire contracts.

### MCP / JSON-RPC boundaries

Do **not** replace JSON on:
- stdio MCP request parsing
- JSON-RPC response envelopes
- current shared-memory request/response payloads

Reason: downstream tools and clients expect JSON-RPC semantics.

### Third-party artifact imports

Do **not** try to force NDA onto:
- `tokenizer.json`
- provider model catalogs
- third-party config payloads

Reason: import compatibility matters more here than internal uniformity.

## Recommended architecture

### NDA-first internal core

For internal semantics, use NDA as the canonical form for:
- plans
- semantic memory
- graph knowledge
- policy registries
- orchestrator facts
- SiteMap metadata and related knowledge records

### JSON compatibility shell

For external interoperability, preserve JSON adapters at:
- provider boundaries
- MCP/JSON-RPC boundaries
- shared-memory transport boundaries
- imported third-party artifact boundaries

### Dual-path execution

Support two execution avenues:
1. **NDA-native harness path** for your custom LLM/runtime when available
2. **JSON compatibility path** for standard provider ecosystems and protocols

The same logical task should be representable once internally, then adapted outward as needed.

## Practical migration rules

When changing a surface, ask:
1. Is this internal and semantic? -> make NDA canonical.
2. Is this external and protocol-bound? -> keep JSON.
3. Is this internal but exposed to JSON clients? -> keep both, with NDA as source of truth.

## Recommended rollout order

1. Instruction registry canonical NDA storage with JSON import/export fallback.
2. SiteMap metadata native-first persistence with JSON fallback.
3. Routed task instruction payloads as NDA contracts.
4. Orchestrator result/checkpoint facts as NDA-backed internal records.
5. Optional NDA transport lane for telemetry or NMCP if the harness benefits from it.

## Bottom line

NDA should not replace JSON everywhere.

NDA should replace **internal semantic authority**.
JSON should remain **external transport and compatibility glue**.

That gives the system:
- better model comprehension
- more deterministic internal memory
- less semantic drift
- compatibility with the existing provider and protocol ecosystem
- a clean path for your custom strict-NDA harness
